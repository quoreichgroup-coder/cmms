# Installer QPM sur les téléphones Android

L’APK autonome se trouve dans `dist/QPM-1.0.53.apk` après compilation. Copiez ce fichier sur chaque téléphone (lien de téléchargement privé, câble USB ou partage de fichiers), ouvrez-le, puis autorisez **Installer des applications inconnues** pour l’application qui ouvre le fichier. Confirmez l’installation et lancez **QPM**. Si Android signale une signature conflictuelle avec une ancienne installation de QPM/Atlas, désinstallez cette ancienne application, puis ouvrez à nouveau l’APK. Les données enregistrées sur le serveur seront toujours disponibles après reconnexion. L’adresse API configurée par défaut est `https://169-58-86-7.sslip.io/api/`. Après la mise à jour, si une ancienne adresse personnalisée est mémorisée, ouvrez **Serveur personnalisé** depuis la connexion et choisissez **Réinitialiser**. Utilisez un compte utilisateur de l’entreprise : l’application mobile est destinée au rôle client, pas au superadmin technique de la plateforme. Les taps de notification ouvrent la ressource associée même si le tap a lancé l’application; la livraison des notifications push requiert les credentials Firebase de l’entreprise.

Cette version requiert Android 7.0 (API 24) ou une version ultérieure. Elle inclut les processeurs ARM 32 bits et 64 bits courants.

Les mises à jour signées doivent conserver le même certificat. Le keystore de production et son mot de passe sont stockés uniquement dans `.build-tools/signing/` et sont exclus de Git. Gardez une copie chiffrée de ce dossier avec vos sauvegardes : sans lui, Android ne peut pas installer une mise à jour par dessus cette version. Le script arrête la compilation si le keystore existe mais que son fichier d’accès manque; il n’en crée pas silencieusement un nouveau.

Pour reconstruire sur une machine de développement, installer Java 17, Android SDK Platform 36 et Node.js 22, puis exécuter `npm ci`, `npm run build:apk` dans ce répertoire. Le premier build télécharge les composants Gradle/Android nécessaires. Pour un serveur différent, définir `API_URL` pendant le build. Firebase, les notifications push et les événements Analytics restent désactivés tant que la configuration Firebase Android de l’entreprise n’est pas fournie.

## Essai sur téléphone après installation

Connectez-vous avec un compte client de l’entreprise sur le même serveur que le web. Dans un ordre de travail existant, ajoutez une photo depuis la galerie, puis une photo prise avec l’appareil. Attendez le message de réussite, quittez la fiche et rouvrez-la : les deux images doivent s’afficher après le rechargement. Dans un commentaire du même ordre, joignez un PDF et vérifiez qu’il reste attaché après l’envoi. Refaites au moins une sélection après avoir refusé une autorisation, puis accordez-la depuis les réglages si le système le demande.

Sur Android, installez 1.0.53 par-dessus la version déjà présente et confirmez que l’application se met à jour sans désinstallation ni perte de session. Essayez aussi un fichier supérieur à 7 Mo : l’application doit afficher le refus de taille et terminer le chargement sans rester bloquée.

Sur iOS, exécutez les mêmes essais avec l’IPA signée distribuée par EAS/TestFlight. Le sélecteur de photos doit s’ouvrir sans solliciter l’accès complet à la photothèque; une photo sélectionnée doit néanmoins être téléversée et réapparaître après réouverture. Testez la caméra séparément : iOS doit alors demander l’autorisation caméra. Aucun essai iOS n’est validé tant qu’une IPA installée sur un appareil réel n’a pas passé ces vérifications.
